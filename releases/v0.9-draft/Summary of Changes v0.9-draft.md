# Summary of Changes — v0.9-draft

**Release type:** **Substantive release — it deliberately changes the operative reading rule of Article 3.** Every prior draft (v0.4.x–v0.8) preserved the standards as written; this one does not. It removes the single sentence that made *everything* in a Street/Road Type a bare minimum — *"All measurements stated for a Type are minimums unless otherwise indicated"* (former §3.C.4) — and replaces it with a **three-layer component-requirement framework**: (1) a **Build-To Standard** — the single value the applicant constructs, stated outright in a new **Build to** column on every Type plate — which the applicant may reduce only on a written demonstration; (2) **bright-line "shall provide where…" triggers** the Code Enforcement Officer can administer without discretion (new §3.F); and (3) **guided Planning-Board discretion** to require fuller components from within the assigned Type, tied to enumerated objectives and a mandatory written finding (new §6.D). It adds a **Master-Plan pre-commitment** rule (Article 8 §13) so a Type and cross-section locked at Master-Plan approval govern later phases, **adds a "Build to" column, a legend, and per-Type footnotes to all ten Type plates**, and adds two **definitions** (Build-To Standard, Provision Component). **No safety standard is touched** — traveled-way width, sight distance (Table 3.2 / §8), intersection geometry (§9), and the maximum grade within 75 ft of an intersection are fixed for every Type and are expressly carved out of every departure, discretion, and waiver mechanism below.

**Folded into this release — a clarity rework of §3.C.** An in-progress cut of this release named the operative value a *"presumptive value"* and annotated the plates by writing that value into the range cell ("10 ft (range 10–15)"). On review that read as loose and buried the value the applicant actually builds. The shipped release renames the term to **Build-To Standard**, gives every Type plate a dedicated **Build to** column that states the value outright, and rewrites §3.C into plain, stepwise prose explaining when and how that value may be altered. No value or rule changed in this rework — only how each is named and displayed. See §3 and §8.

**Folded into this release — a notation change.** At the same time, every Street and Road **Type code drops its hyphen**: S-1 … S-5 become **S1 … S5** and R-1 … R-5 become **R1 … R5** (the Driveway "D" is unchanged). This is a global, purely editorial relabeling — no Type, standard, range, district assignment, or cross-reference moves; only the spelling of the code label changes. It is applied across the Code, the ten Type plates, the definitions, the build pipeline, and the supporting memos. See §17.

**Compares against:** [v0.8-draft](../v0.8-draft/). A draft-to-draft `diff-pdf` overlay ships as *Redline — Full CZC v0.9-draft vs v0.8-draft.pdf* (the meaningful diff for this release); a *Redline — Full CZC v0.9-draft vs Baseline.pdf* is included for completeness with the standing page-misalignment caveat (see §12).

**Why this release exists.** v0.8 finished the form-based Type system — ten one-stop Type pages, each carrying its own design-standards strip. But the strips inherited a fatal default from the legacy ordinance: a flat *"all measurements are minimums."* A minimum is, by definition, the floor, and nothing in the code ever required more — so every Street and Road would lawfully be built to the **narrowest sidewalk, no planting strip, no street trees, no on-street parking.** An S1 Main Street built to minimums is not a Main Street; the place-based typology defeats itself. The discussion memo *Requiring Street & Road Components* worked the problem to six locked decisions (memo §9, drafter's recommendations folded in). This release implements them. The discretion layer is drafted to *Cope v. Brunswick*, 464 A.2d 223 (Me. 1983): a board may exercise design discretion only where the ordinance keys that discretion to **enumerated criteria** and requires **written findings** — which §6.D supplies, while reserving the CEO's role to bright-line triggers only.

The transect weighting is deliberate: the "require more" pressure is **strong** in the Street family, in D5–D6, and in the villages, and is **off** in the rural Road family (the 2018 Comprehensive Plan favors "less road" and minimal land alteration in the rural Districts). D2 is treated as village-side.

## 2. The component-requirement framework — three layers

The framework is intentionally layered by *who administers it* and *how much judgment it requires*, so the routine case is mechanical and only the genuinely discretionary case reaches the Board.

- **Layer 1 — Build-To Standards (§3.C.2 / §3.C.4).** A range no longer means "build the floor." Each Type page states a **Build-To Standard** in a dedicated **Build to** column — the value the applicant builds unless a written demonstration justifies less. For the **pedestrian/landscape components** (sidewalk, planting strip, street trees, on-street parking) the Build-To Standard is the **fuller** end, and within the Street family those components are **built**. For the **traffic-calming dimensions** (travel-lane width, curb-return radius) it is the **lower** end in every Type — narrower lanes and tighter curb returns slow traffic; the lower value is a floor that may be *widened* for vehicle access but not narrowed. Administered by the CEO; no discretion.
- **Layer 2 — Bright-line "shall provide where…" triggers (§3.F).** Six enumerated conditions that *require* a component outright — e.g., sidewalk both sides in D5/D6; one side within ¼ mile of a school/Town Office/library/post office/park/landing/place of public assembly; one side where a new Street serves more than [12] dwelling units. These are objective facts the CEO can check on a permit without weighing anything.
- **Layer 3 — Guided Planning-Board discretion (§6.D).** Where neither a Build-To Standard nor a §3.F trigger settles the question, the Board may require fuller components **from within the assigned Type's range**, but only to serve one of six enumerated objectives and only on a **written finding**. The Board may never exceed the assigned Type (the ceiling); a fuller cross-section requires reclassifying the segment to a higher Type.

## 3. The §3.C rewrite — before / after (the operative change)

This is the heart of the release, and the section the v0.9 clarity pass reworked most. §3.C (GENERAL) now opens by naming the two columns that appear on every Type page, defines the **Build-To Standard**, and sets out — in plain, stepwise paragraphs — exactly when and how that standard may be altered.

**§3.C.1 — the two columns (new framing).**

> "Each Type's design standards are stated on that Type's page in Section 2 in two columns. The **Type standard** column states the range or choice of options the Type authorizes. The **Build to** column states the single value to be constructed — the **Build-To Standard** defined in Section 3.C.2. The rules in this Subsection govern how the two columns are read and applied."

**§3.C.2 — how a range is read.**

> *Before (v0.8):* "Where a range is given (e.g., "10–11 ft"), the value selected within the range must be supported by an engineering justification submitted with the application."

> *After (v0.9):* "The **Build-To Standard** is the value stated in the **Build to** column on the Type's page in Section 2. It is the value the applicant constructs, subject to alteration only as Section 3.C.4 provides. Where the Type standard is a single value, the Build-To Standard restates it. Where the Type standard is a range (for example, "8–12 ft") or a choice of sides, the Build-To Standard is drawn from it as follows: (a) for the pedestrian and landscape components — sidewalk width, planting strip, street trees, and on-street parking — the Build-To Standard is the fuller value, and within the Street family (Types S1 through S5) these components are built; and (b) for the traffic-calming dimensions — travel-lane width and curb-return radius — the Build-To Standard is the lower value."

**§3.C.4 — the configuration to be built (replaces the "minimums" sentence).**

> *Before (v0.8):* "All measurements stated for a Type are minimums unless otherwise indicated."

> *After (v0.9):* "The Build-To Standard, together with the components stated for a Type, is the configuration to be built. It may be altered only as this Subsection provides: **(a) Reducing a pedestrian or landscape component** — an applicant may build a sidewalk, planting strip, street-tree provision, or on-street parking narrower than its Build-To Standard, or omit such a component, only upon a written demonstration … that (i) every safety-critical standard of this Article is met, and (ii) the reduced configuration better serves the purpose of the assigned Type in its District context …; a component required under §3.F may not be reduced or omitted except as that Section provides. **(b) Widening a traffic-calming dimension** — the travel-lane width and curb-return radius build to the lower value because a narrower lane and a tighter corner slow traffic and shorten pedestrian crossings; they may be built wider … to accommodate truck, bus, or emergency-vehicle movements; they shall not be built narrower. **(c) Safety-critical standards are fixed** — the traveled-way width, the sight distances of Table 3.2 and Section 8, the intersection geometry of Section 9, and the maximum grade within 75 ft of an intersection (Section 9) are fixed for every Type and may not be reduced under this Subsection. **(d) Building below a minimum** — a departure under paragraph a alters the Build-To Standard within the Type's stated range and is processed as part of the application; it is not a waiver. To build below a stated minimum of the assigned Type, a waiver under Section 13.H is required."

The rewritten §3.C does four jobs: it names the two columns so the operative value reads off the page, it defines the **Build-To Standard** as that value, it sorts the alteration rules into four plain paragraphs (reduce a pedestrian/landscape component on a demonstration; widen — never narrow — a traffic-calming dimension; safety stays fixed; go below a minimum only by waiver), and it keeps the **departure-vs-waiver** line crisp. §3.C.3 ("per MaineDOT") and §3.C.5 (R3 passing pull-outs, relocated intact in v0.8) are unchanged.

## 4. §3.F Required Components by Context (Layer 2 — bright-line triggers)

A new Subsection **§3.F REQUIRED COMPONENTS BY CONTEXT** is appended after §3.E (Basis for Maximum Grades) — no renumbering, it is the next letter. Seven items, all CEO-administrable:

1. **Preface.** Applies regardless of whether a component's dimension is a Build-To Standard or a minimum; administered by the CEO on CEO-issued permits under §13.C and by the Planning Board on Subdivision and Master-Plan review.
2. **Sidewalk** — required (a) both sides in D5 Village Business and D6 Town Center; (b) one side where any frontage lies within **¼ mile** (measured along the public way) of a **school, the Town Office, the library, the post office, a public park or public landing, or a place of public assembly**; (c) one side where the segment connects to an existing sidewalk; (d) one side where a new Street serves more than **[12]** dwelling units.
3. **On-street parking** — one side where the abutting frontage permits a ground-floor retail, restaurant, or personal-service use under Articles 2 and 7.
4. **Planting strip + street trees** — on any segment with a required sidewalk, unless the CEO finds in writing that a planting strip is infeasible (utility conflict, insufficient ROW after safety-critical widths, or ledge).
5. **Connectivity** — a new Street connects to any stubbed street abutting the parcel and stubs to each abutting developable parcel where a future through-connection is feasible.
6. **Trail connection** — where an adopted Town trail/path/sidewalk plan shows a connection across or along the parcel, the Street or Road accommodates it.
7. **Road-family limit** — Types R1 through R5 are **exempt** from §§3.F.2–3.F.4 **except** where the segment abuts D5 or D6 frontage. This is the transect weighting made operative: rural Roads carry no pedestrian-component triggers.

## 5. §6.D Determination of Components & Widths (Layer 3), and the §6 renumber map

A new Subsection **§6.D DETERMINATION OF COMPONENTS AND WIDTHS** is inserted after §6.C (Type Assignment), pushing the three following subsections down one letter:

| Subsection | v0.8 | **v0.9** |
|---|---|---|
| Type Assignment | §6.C | §6.C *(unchanged)* |
| **Determination of Components & Widths** | — | **§6.D *(new)*** |
| Design Standards | §6.D | **§6.E** |
| Construction & Inspection | §6.E | **§6.F** |
| Acceptance as a Town Way | §6.F | **§6.G** |

The new §6.D, four items:

1. The Planning Board may require components and widths **from within the assigned Type's stated ranges and options** to serve one or more enumerated objectives: (a) pedestrian safety and comfort per §2.C.3; (b) continuity of the street, sidewalk, and block network; (c) District character and the Comprehensive Plan; (d) stormwater management and tree canopy; (e) emergency-vehicle access; (f) on-street parking supply.
2. Any such requirement **shall be supported by a written finding** identifying the objective and the basis for it, made as part of the Subdivision findings under Article 8 §12.F or the Master-Plan findings under Article 8 §13.E.
3. **Ceiling.** The Board may not require a configuration exceeding the assigned Type; a fuller cross-section is available only by reclassifying the segment to a higher Type under §5.E.
4. In Types R1 through R3 the Board **shall weigh rural character and minimal land alteration** against the objectives in §6.D.1 (transect weighting, again, made operative).

Items 1 (enumerated objectives) and 2 (mandatory written finding), with the §6.D.3 ceiling and the §13.C.4 reservation of discretion to the Board, are the **Cope-compliance spine** of the framework. Every internal cross-reference that pointed at the old §6.D–§6.F was repointed (see §14); the one external stale reference at §11.C.2 — "accepted as a Town Way per Section 6.F" — now reads **§6.G**.

## 6. Master-Plan pre-commitment (Option D) — Article 8 §13

Decision D of the memo: the Type and cross-section should be **fixed at Master-Plan approval** and govern subsequent phases, so a developer cannot lock in a generous concept plan and then build phase-by-phase to the floor. Two edits in `article-08-administration.md`:

- **§13.A.2** — the existing "Street and Road Types per Article 3" verification item now reads "Street and Road Types **and cross-section configurations** per Article 3."
- **§13.E.2 *(new)*** — "At Master Plan approval, the Type and cross-section configuration of each Street and Road within the plan are fixed and govern subsequent project phases. A later phase may propose a different Type or cross-section configuration only by a revision of the Master Plan under Section 14."

**Placement note (deviation from the approved plan — logged in §15):** the plan sketched this as *§13.E.1.e*, i.e., a fifth item in the §13.E.1 list. But §13.E.1 reads "…upon verifying consistency to the following:" and items a–d are *things the Master Plan must be consistent with*. A forward-looking pre-commitment rule is not a consistency criterion and cannot grammatically be an item in that list. It is placed instead as **§13.E.2**, a sibling of §13.E.1. Article 3 §6.D.2 references "the Master Plan findings under Article 8 §13.E" broadly, so the cross-reference still resolves.

## 7. Administration split & waivers — §13.C.4 and §13.H.2 (Article 3)

Two edits confirm *who does what* and keep the CEO's role bright-line (memo Decision 6, *Cope*):

- **§13.C.4 *(new)*** — "The Code Enforcement Officer administers the Build-To Standards of Section 3.C and the contextual component requirements of Section 3.F on permits the Officer issues, and states any infeasibility finding under Section 3.F.4 in writing. The discretion to require fuller components and widths under Section 6.D is reserved to the Planning Board."
- **§13.H.2 *(new, appended to waivers)*** — "A departure from a Build-To Standard under Section 3.C.4 is processed as part of the application and is not a waiver under this Subsection. A waiver under this Subsection is required only to build below a stated minimum of the assigned Type, and no waiver may be granted from the safety-critical standards listed in Section 3.C.4."

Together these settle the procedural paths cleanly: **departure** from a Build-To Standard (application demonstration, §3.C.4) → **bright-line trigger** (CEO, §3.F) → **discretionary increase** (Board + written finding, §6.D) → **waiver below a minimum** (§13.H), with safety unwaivable throughout.

## 8. Plate annotations — the "Build to" column, legend + per-Type footnotes (all ten)

Every Type page now states the operative value on its face. Three changes:

- **A third column on the Design Standards strip.** Each standards row now carries the **Type standard** (the authorized range or option, set in gray as a reference) and, alongside it, the **Build to** value — the Build-To Standard, set bold and dark so the value to construct reads at a glance. Examples on S1: Right-of-way `66–80 ft → 80 ft`; Traveled way `20–22 ft · 2 lanes @ 10–11 ft → 20 ft · 2 @ 10 ft`; On-street parking `Both sides · 7–8 ft → Both sides · 8 ft`; Planting strip `5–8 ft, both sides → 8 ft, both sides`; Sidewalk `8–12 ft, both sides → 12 ft, both sides`; Street trees `Required → Both sides`; Curb return radius `10–15 ft → 10 ft` (the lower, traffic-calming value); the fixed/reference rows (Design speed, Max. grade, Max. block length, Sight distance, Pavement, Surface) restate the same value in both columns.
- **`source/exhibits/cross-sections/types.json`** — every standards row was converted from a `[label, value]` pair to a `[label, type-standard, build-to]` triple (140 rows across the ten Types, format-preserving line rewrite), and a one-line `"footnote"` was added/updated on each context-bearing Type pointing to the governing §3.C / §3.F rule. The build-to value follows the §3.C.2 rule: the fuller value for pedestrian/landscape components, the lower value for the traffic-calming dimensions, the same value restated for fixed rows; ROW builds to the end of the range that contains the built section.
- **`source/cross-section-plates.typ`** — `standards_strip()` was rewritten to a three-column table (Component | Type standard | Build to) with bold-dark build-to cells under a `TYPE STANDARD` / `BUILD TO` header rule, and the trailing annotation block was reworded to a **Build-To legend** (gray 7 pt italic, matching the credit-caption style so it reads as an annotation rather than another standards row): *"Build to the right-hand column (Art. 3 §3.C): the fuller value for pedestrian and landscape components (reducible only on the written demonstration of §3.C.4), the lower value for the traffic-calming dimensions (a safety floor). Components marked "where …" are required by context under §3.F; the Board may require fuller components within the assigned Type under §6.D."* followed by `t.footnote` on its own line where present (`below: 13pt` keeps the following Target Districts / Character panels clear).

Adding a column roughly doubles the strip's row height, so plate parity (10 plates = 10 pages, even `page_offset`) was the gate; it was confirmed empirically — the strip renders at 7.5 pt with the cross-section image at its existing 180 pt cap, and the plate block holds at exactly ten pages.

## 9. Definitions added — Article 9

Two terms live in the "DEFINITIONS ADDED FOR ARTICLE 3" block:

- **Build-To Standard** *(alphabetized between Alley and Cartway)* — "The value stated in the "Build to" column on a Type's page in Article 3 Section 2 — the configuration the applicant is to construct for that Type. It is drawn from the Type's authorized range under Article 3 Section 3.C.2 (the fuller value for the pedestrian and landscape components, the lower value for the traffic-calming dimensions). A Build-To Standard is distinguished from a minimum, which is the floor below which a waiver is required: an applicant may build less than a Build-To Standard by the written demonstration of Article 3 Section 3.C.4, whereas building below a stated minimum requires a waiver under Article 3 Section 13.H."
- **Provision Component** *(between Planting Strip and Public Easement)* — "A Street element — a sidewalk, planting strip, street trees, or on-street parking — whose presence on a given segment is governed by the context triggers of Article 3 Section 3.F rather than by a fixed dimension stated for the Type."

## 10. The safety carve-out — what did NOT change

Safety is the one thing this release is forbidden to touch, and it doesn't:

- **No safety standard became reducible.** §3.C.4.c names the four safety-critical standards — **traveled-way width, sight distance (Table 3.2, Section 8), intersection geometry (Section 9), and the maximum grade within 75 ft of an intersection (Section 9)** — as fixed for every Type and outside the departure mechanism. §6.D's ceiling forbids the Board from exceeding the Type, and §13.H bars any waiver of those four standards.
- **The traffic-calming Build-To is a floor, not a reduction.** Travel-lane width and curb-return radius build to the *lower* value because narrow lanes and tight corners calm traffic; §3.C.4.b lets them be *widened* for truck/bus/emergency access but never narrowed. The narrow value is the safety floor, not a relaxation.
- **The plate "Build to" column preserves every safety value.** On the safety and reference rows the Build to simply restates the fixed value (Sight distance `Per Table 3.2 → Per Table 3.2`; Pavement `Per Table 3.3 → Per Table 3.3`; Surface `Paved → Paved`); the Traveled way builds to the narrow lane configuration, which §3.C.4 fixes as the floor. No safety value is lowered anywhere on any plate.
- **Tables 3.2 (sight distance) and 3.3 (construction) are byte-unchanged from v0.8.** The only place "Table 3.2" newly appears is inside the §3.C.4 carve-out prose and the plate Build to column naming it as protected — not a table edit.
- **§§8–11 geometry and §12 MaineDOT coordination are untouched.** R4/R5 cartway geometry stays "Per MaineDOT."
- **No regulatory value was deleted.** The framework changes how a *range* is read and what is *required*; it removes no width, speed, grade, or block-length figure. The R3 passing-pull-out rule (§3.C.5) is unchanged.

## 11. Board-settable values flagged for the Planning Board

These are policy levers the draft sets to a reasonable default and flags for the Board to confirm or change at adoption:

- **[12] dwelling units** — the threshold at which a new Street triggers a one-side sidewalk (§3.F.2.d). Shown bracketed in the draft.
- **The ¼-mile radius and the destination list** — school, Town Office, library, post office, public park or public landing, place of public assembly (§3.F.2.b). The radius and the roster are both policy choices.
- **The Build-To values** — the right-hand "Build to" column entries in `types.json`; the Board may calibrate which value within each range the Type builds to (and, for ROW, which width drives the cross-section illustrations).
- **D2's placement on the village side of the transect** — the framework treats D2 as village-side (so D2 streets lean toward the fuller, sidewalk-bearing Build-To configuration). If the Board reads D2 as more rural, the §3.F.7 Road-family exemption and the §6.D.4 rural-character weighing would need to extend to it.

## 15. Deviations from the approved plan (logged)

Five conscious departures from the plan-as-written, each made for correctness and each disclosed here:

## 17. Type-code notation — the hyphen is dropped (S-1 → S1)

This release also adopts a notation change requested for readability: every Street and Road **Type code drops its hyphen** — S-1 … S-5 become **S1 … S5**, and R-1 … R-5 become **R1 … R5**. The Driveway (D) is unaffected. This is a global, purely editorial change: **no Type, standard, range, district assignment, or cross-reference is altered** — only the spelling of the code label.

The change was applied as a single verified substitution (`\b[SR]-[1-5]\b` → no hyphen) across the entire working tree after confirming **zero false positives** (the only `[A-Z]-[1-5]` pattern anywhere in the source is a Type code; "US Route 1" and "CC BY-SA" do not match the pattern). It touched **301 occurrences** in 13 source/build/memo/style files, plus 2 in the unbuilt legacy Article 2. The ten cross-section illustrations were renamed on disk (`S-1.svg → S1.svg … R-5.svg → R5.svg`); their content is code-agnostic (the badge is drawn by the plate layout, not baked into the SVG), and the compositor writes `{code}.svg` from the Type code, so it stays consistent.

The notation propagates automatically to the **plate badges** (drawn from `t.code`), the **auto-TOC labels** (built as `code + name`, now "S1 Main Street" … "R5 Rural Highway"), and the **cross-section file lookups** (`t.code + ".svg"`). The frozen `releases/v0.2 … v0.8` snapshots retain the old hyphenated notation by design — they are published point-in-time artifacts. The v0.9 redlines therefore show the S-1 → S1 change on every Type reference, alongside the framework edits.
